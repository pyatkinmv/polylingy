## 1. Содержание

```
Курс
 ├─ Юнит (необязателен): название, теория (одна страница)
 │   └─ Топик: название, объяснение
 │       └─ Упражнение: тип, содержимое, объяснение
 └─ …
```

- **Курс** — то, что импортируется одним файлом. Политики задаются только на курс.
- **Юнит** — подкурс: страница теории и топики по ней. Юниты необязательны: курс либо
  плоский (топики сразу в курсе, как сейчас), либо целиком из юнитов.
- **Топик** — то, что осваивается и повторяется. Одна тема на какую-то часть теории
  (в учебнике это, например, «упражнение 1.1»). Как автор разбил теорию на пункты, модели неважно.
- **Упражнение** — одно задание целиком: одно предложение, 6 предложений с пропусками, набор пар
  на соответствие и т. п. В топике много однотипных упражнений; при показе выбирается случайное.
  Упражнение состоит из **пунктов** (пропусков, пар) — от одного до скольких угодно; проверка оценивает
  каждый пункт. У пункта может быть несколько верных вариантов ответа
  (`localization` / `localisation`, `is working` / `'s working`).

## 2. Словарь

| Термин | Что это | Пример |
|---|---|---|
| **Ответ** | Что пользователь сделал с одним упражнением: ввод и, если есть, самооценка | заполнил 6 пропусков; нажал «Hard» |
| **Результат проверки** | Что сказала проверка типа упражнения: какие пункты верны | 5 из 6 |
| **Оценка (Grade)** | Как курс засчитал ответ. Тип оценки задают политики курса | `PASS`, `FAIL`; или `AGAIN/HARD/GOOD/EASY` |
| **Раунд** | Одно прохождение топика: оценки от первого ответа до освоения | `[PASS, FAIL, PASS, PASS, PASS]` |
| **Фаза** | Какой это раунд: `LEARNING` (топик ещё ни разу не освоен) или `REVIEW` | |
| **Память топика** | Что расписание помнит о топике между раундами. Своя у каждого расписания | SM-2: EF 2.5, интервал 3 дня; Лейтнер: коробка 2 |
| **Срок** | Дата, с которой топик снова нужно повторять | четверг |

Сессий в модели нет: для логики они не нужны. Если понадобятся для статистики, их можно
вывести из журнала позже.

## 3. Конвейер одного ответа

```
Ответ на упражнение
  │ ① Проверка — зависит от ТИПА упражнения (пропуски, соответствия…)
  ▼
Результат проверки (5 из 6) + самооценка (если курс её спрашивает)
  │ ② Оценивание — политика курса
  ▼
Оценка (PASS)            ──► добавляется в текущий раунд
  │ ③ Освоение — политика курса, знает фазу
  ▼
раунд продолжается  │  топик освоен
                    │ ④ Расписание — политика курса
                    ▼
               новая память топика и срок; раунд очищается

⑤ Порядок — политика курса: какой топик показать следующим
```

Проверка — свойство типа упражнения, а не курса. Остальные четыре шага — **политики курса**.

### Проверка, варианты и опечатки

Тип упражнения знает, из каких пунктов оно состоит и как сравнить ответ на пункт. Для текстовых
пунктов сравнение общее и настраивается курсом:

- ответ сравнивается со **всеми верными вариантами** пункта;
- перед сравнением обе строки нормализуются: регистр не важен, пробелы по краям убираются,
  несколько пробелов подряд считаются одним, точка в конце не важна, все виды апострофа
  (`'`, `’`, `‘`, `ʼ`, `` ` ``) считаются одним символом `'`; сам апостроф значим: `dont` ≠ `don't`;
- если курс разрешает опечатки (настройка курса), ответ на расстоянии одной опечатки от варианта
  засчитывается с пометкой «опечатка», и пользователь видит, как правильно.

Нормализация и определение опечатки живут **в одном месте** — `TextMatcher` в `core/rules`:
чистая функция `match(input, variants, allowTypos): CORRECT | TYPO | WRONG` со своим набором
табличных тестов. Типы упражнений только вызывают её и сами строки не сравнивают.

Результат каждого пункта — `CORRECT`, `TYPO` или `WRONG`. Засчитывать ли `TYPO`, решает оценивание:
в строгом курсе это ошибка, в обычном — нет.

Опасность: в грамматике опечатка часто и есть ошибка (`a`/`an`, `work`/`works`, `then`/`than`).
Поэтому на первой итерации опечаткой считаются только **замена одной буквы или перестановка двух
соседних** в слове **от 4 букв**, не больше одной на пункт. Пропущенная или лишняя буква — не опечатка:
так выглядят ошибки в окончаниях (`-s`, `-ed`, `-ing`).

Самооценка — отдельная настройка курса: в одних курсах её спрашивают, в других нет.

## 4. Политики курса

| Политика | Получает | Отдаёт | Примеры |
|---|---|---|---|
| **Оценивание** `GradingRule<G>` | результат проверки, самооценку | оценку `G` или «не учитывать» | все пункты верны → PASS; ≥ 80 % → PASS; кнопка самооценки |
| **Освоение** `MasteryPolicy<G>` | оценки текущего раунда, фазу | освоен топик или нет | 3 подряд при изучении и 1 при повторении; 2 подряд; до первого GOOD |
| **Расписание** `Scheduler<M, G>` | память, оценки завершённого раунда, сегодня | новую память (в ней срок) | SM-2; коробки Лейтнера; Anki-подобное |
| **Порядок** `TopicPicker` | доступные топики по порядку курса, текущий топик | следующий топик | сначала повторения, потом новое по порядку; случайный |

Одна политика освоения работает и для изучения, и для повторения: она получает фазу и
сама решает, отличаются ли правила. Отдельной политики повторения нет.

## 5. Интерфейсы (предложение)

```kotlin
enum class Phase { LEARNING, REVIEW }

/** Один засчитанный ответ раунда: оценка плюс исходные факты, если политике нужно больше. */
data class Attempt<G>(val grade: G, val check: CheckResult?, val at: ZonedInstant)
typealias Round<G> = List<Attempt<G>>

/** Из ответа (ввод, самооценка, всё, что есть в событии) и результата проверки получить оценку.
 *  null — ответ не учитывать. */
fun interface GradingRule<G> {
    fun grade(answer: AnswerSubmitted, check: CheckResult?): G?
}

/** Весь текущий раунд целиком: освоен ли топик? */
fun interface MasteryPolicy<G> {
    fun isMastered(round: Round<G>, phase: Phase): Boolean
}

/** Раунд завершён: по всему раунду обновить память топика. memory == null — топик осваивается впервые. */
interface Scheduler<M, G> {
    fun schedule(memory: M?, round: Round<G>, today: LocalDate): M
    fun dueDate(memory: M): LocalDate
}

/** Какой топик дальше. Кандидаты идут в порядке курса. */
fun interface TopicPicker {
    fun pick(candidates: List<Candidate>, current: Uuid?): Uuid?
}
data class Candidate(val topicId: Uuid, val phase: Phase)

/** Набор политик курса. Типы гарантируют, что оценивание, освоение и расписание совместимы. */
class CourseRules<M, G>(
    val grading: GradingRule<G>,
    val mastery: MasteryPolicy<G>,
    val scheduler: Scheduler<M, G>,
    val picker: TopicPicker,
)
```

Состояние топика, которое выводит `replay()`:

```kotlin
data class TopicState<M, G>(
    val memory: M?,          // null — топик ещё ни разу не освоен
    val round: List<G>,      // оценки текущего, незавершённого раунда
) {
    val phase get() = if (memory == null) Phase.LEARNING else Phase.REVIEW
}
```

Топик доступен сегодня, если он новый, если раунд начат и не закончен, или если наступил срок.

### За счёт чего политики гибкие

Политики — **чистые функции над полными данными**, без собственного состояния:

- оценивание получает событие ответа целиком: новые факты в журнале (например, время на ответ)
  становятся доступны без смены интерфейса;
- освоение получает **весь раунд**, а не счётчик серии — любая формула над историей раунда возможна;
- расписание получает **весь раунд** и свою память `M` произвольной формы — качество раунда
  (сколько ошибок, какие оценки, сколько ответов) оно считает само;
- тип оценки `G` — параметр, поэтому шкала из 4 уровней работает так же, как PASS/FAIL.

Новая политика — это новый класс, интерфейсы не меняются. В файле курса задаются только тип
политики и её параметры; формул и скриптов в JSON нет.

Примеры, которые укладываются в эти интерфейсы (не реализуем сейчас):

```kotlin
// «2 подряд, а если в раунде была ошибка — 3 подряд»
class AdaptiveConsecutive(val clean: Int = 2, val afterError: Int = 3) : MasteryPolicy<PassFail> {
    override fun isMastered(round: Round<PassFail>, phase: Phase): Boolean {
        val need = if (round.any { it.grade == FAIL }) afterError else clean
        return round.takeLastWhile { it.grade == PASS }.size >= need
    }
}

// Шаги как в Anki: AGAIN — в начало, HARD — на месте, GOOD — шаг вперёд, EASY — сразу освоен
class AnkiSteps(val steps: Int = 2) : MasteryPolicy<AnkiGrade> {
    override fun isMastered(round: Round<AnkiGrade>, phase: Phase): Boolean {
        if (phase == Phase.REVIEW) return round.last().grade != AGAIN
        var pos = 0
        for (a in round) when (a.grade) {
            AGAIN -> pos = 0
            HARD -> {}
            GOOD -> pos++
            EASY -> return true
        }
        return pos >= steps
    }
}

// Расписание по качеству раунда: чем чище раунд, тем дальше срок
class QualityLadder : Scheduler<Int, AnkiGrade> { /* память — номер ступени */ }

// Оценивание в 4 уровня без кнопок: по проверке и времени
val AutoAnki = GradingRule<AnkiGrade> { answer, check -> when {
    check == null -> answer.rating?.toAnkiGrade()
    check.wrong > 0 -> AGAIN
    check.typos > 0 -> HARD
    else -> GOOD          // EASY — например, если ответ дан быстро (когда в журнале появится время)
} }
```

### Оценка: почему типы, а не число

Рассматривались три варианта: фиксированные 4 уровня для всех, число от 0 до 1 и тип оценки,
который задают политики. Предлагается третий:

- ядро не привязано ни к 2, ни к 4 кнопкам;
- число 0…1 теряет смысл: «Hard» — это 0.6 или 0.7? Расписанию в стиле Anki нужна именно нажатая кнопка;
- компилятор не даст собрать курс, где оценивание выдаёт `AnkiGrade`, а расписание ждёт `PassFail`;
- доля верных пунктов («5 из 6») не теряется: она в результате проверки, и оценивание само решает,
  что она значит.

Типы оценок, которые понадобятся первыми:

```kotlin
enum class PassFail { PASS, FAIL }
enum class AnkiGrade { AGAIN, HARD, GOOD, EASY }
```

В файле курса политики записаны данными:

```json
"rules": {
  "grading":   { "type": "threshold", "min": 0.8 },
  "mastery":   { "type": "consecutive", "learning": 3, "review": 1 },
  "scheduler": { "type": "sm2" },
  "picker":    { "type": "reviews-first" }
}
```

Реестр политик собирает из этого `CourseRules`. Несовместимую пару (оценивание даёт `AnkiGrade`,
а SM-2 ждёт `PassFail`) реестр отвергает при импорте с понятной ошибкой.
Без `rules` курс получает политики по умолчанию — те, что работают сейчас.

## 6. Пример: простейшие политики в разных сочетаниях

Простейшие политики:

| Политика | Варианты |
|---|---|
| Проверка | опечатки запрещены / разрешены |
| Оценивание | «всё верно» — все пункты верны; «порог 75 %» |
| Освоение | «N подряд», N = 1 или 3 |
| Расписание | «лестница» 1 · 3 · 7 · 14 · 30 дней: раунд без ошибок — ступень выше, с ошибками — первая ступень |
| Порядок | по порядку |

Топик «Present continuous», упражнения разного размера: на 1, 2 и 4 пропуска.
Ответы в понедельник (изучение):

| № | Упражнение | Пункты |
|---|---|---|
| 1 | 1 пропуск | `'s working` — верно (это второй вариант ответа) |
| 2 | 4 пропуска | 3 верно, 1 неверно |
| 3 | 2 пропуска | 1 верно, 1 с опечаткой (`is wroking`) |
| 4 | 1 пропуск | верно |
| 5 | 4 пропуска | все верно |
| 6 | 2 пропуска | все верно |

| Сочетание | Оценки по ответам | Итог |
|---|---|---|
| опечатки да, всё верно, 1 подряд | P | освоен с 1-го ответа, ступень 1 → завтра |
| опечатки нет, всё верно, 3 подряд | P F F P P P | освоен с 6-го ответа, ступень 1 → завтра |
| опечатки да, всё верно, 3 подряд | P F P P P | освоен с 5-го ответа |
| опечатки нет, порог 75 %, 3 подряд | P P F P P P | освоен с 6-го ответа (3/4 = 75 % засчитано, 1/2 — нет) |

На следующий день — повторение. Без ошибок в раунде топик идёт на ступень 2 (3 дня),
с ошибкой — снова на ступень 1 (завтра).

### Как в этой модели выглядит Anki

Здесь схема Anki упрощена, но в модель она укладывается. Оценка — `AnkiGrade`. Освоение при изучении
идёт по шагам: `AGAIN` — к первому шагу, `GOOD` — на шаг вперёд, `EASY` — сразу освоен.
При повторении хватает одного ответа не `AGAIN`. Расписание в стиле SM-2 учитывает нажатые кнопки.
Чего в модели нет: в Anki шаги изучения разнесены по времени (1 мин, 10 мин), у нас топик в раунде
доступен сразу.

## 7. Порядок, юниты и теория

- **Вход в юнит**: кандидаты — топики юнита. **Вход в курс**: кандидаты — топики всех юнитов по порядку.
  Пикер один и тот же.
- **По умолчанию** (`reviews-first`): сначала топики к повторению, затем новые, оба списка в порядке
  курса. Пикер остаётся на текущем топике, пока раунд не закончен, — получается конвейер 1.1 → 1.2 → …
- Какой юнит открыть, решает пользователь, а не пикер.
- **Теория юнита** открывается сама, если в журнале нет ни одного ответа ни по одному топику юнита.
  Иначе — только по кнопке «Теория», которая доступна всегда. Флаг «теория прочитана» не хранится.
- Ушёл посреди раунда — при следующем входе раунд продолжается: он восстанавливается из журнала.

## 8. Что хранится

Журнал хранит **факты**: ввод, результат проверки по пунктам, самооценку. Оценки, раунды и
память не хранятся — их каждый раз выводит `replay()` по текущим политикам курса.
Следствие: если поменять политики курса, прогресс пересчитается по всей истории.

## 10. Открытые вопросы

- Как устроен результат проверки для нетекстовых типов упражнений (соответствия, расстановка).

Сознательные ограничения:
- **топики независимы**: политики видят только историю одного топика, связей между топиками нет;
- **задержек внутри раунда нет** (в отличие от шагов Anki «повторить через 10 минут»):
  топик в незаконченном раунде доступен сразу;
- юнит считается освоенным, когда освоены все его топики; это вычисляется для отображения
  (отметка в списке юнитов), отдельной политики нет.

Отложено, не делаем сейчас:
- лимит новых топиков в день.

Решено:
- самооценка — настройка курса;
- теория юнита показывается сама и при входе в курс, когда пикер впервые доходит до топика
  юнита, в котором ещё нет ни одного ответа.
