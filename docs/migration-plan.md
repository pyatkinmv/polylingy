## 0. Как ведём работу

- Новая версия **несовместима** со старой: старый формат курса, старый журнал и старую базу не поддерживаем и не переносим.
- Ветка **`next`** от `master`. Каждый этап — своя ветка от `next` (`stage/1-content-model`, …) и мерж обратно в `next`.
  В `master` всё попадает **одним мержем** на этапе 8 как **0.2.0**. До этого в `master` остаётся рабочая 0.1.0.
- Каждый этап заканчивается:
  - зелёным `./gradlew check`;
  - для этапов с экранами — скриншотами, которые я просматриваю, и перезапуском приложения.
- Старые классы удаляются на том этапе, где их заменили; к концу в коде не остаётся двух моделей.
- **Если по ходу встречается решение, которого нет в документах, — останавливаюсь и спрашиваю**,
  а не придумываю. Найденные ответы дописываются в `learning-model.md` / `content-format.md`.

## 3. Этапы

### Этап 1. Модуль `content`: модель, разметка, разбор, проверка — сделано

Новый Gradle-модуль `:content` (KMP, `commonMain`, пакет `com.polylingy.content`). Зависимости: только kotlinx-serialization.

Что пишем:
- `Inline` — разбор строки в узлы: текст, `**жирный**`, `*курсив*`, `{{пропуск|варианты}}`, перенос.
  Ошибки разметки — с позицией.
- `Image(src, alt, caption?)`, `Side` (текст или картинка), таблица.
- `Block` — sealed: `section`, `text`, `situation`, `image`, `table`, `quote`, `examples`, `words`, `tip`, `seeAlso`;
  плюс `Unknown` для мягкого режима.
- `Content` — sealed: `Blocks` (`markdown` и `html` — TODO, в модели не заводим, пока не нужны).
- `Exercise` — sealed: `Gaps`, `Choice`, `Pictures`, `Table`, `Match`, `Order`, плюс `Unknown`; общие поля
  (`id`, `instruction`, `explanation`) — в интерфейсе, JSON плоский.
- `Response` — sealed: что ввёл ученик (`Blanks` — для gaps, pictures и table; `Choice`, `Match`, `Order`). `@Serializable`: оно пойдёт в журнал.
- `ItemResult` (`CORRECT` / `TYPO` / `WRONG`) — здесь же, потому что его показывает `ExerciseView`.
- `validate(at: Path): List<Problem>` у каждого типа и блока: правила из content-format, раздел 5.
- `ContentJson` — строгий kotlinx-`Json` с `"type"` как дискриминатором и мягкий вариант для более новых файлов
  (незнакомые поля игнорируются, незнакомые типы становятся `Unknown`).

Тесты (`commonTest`):
- разметка: таблица строк → узлы и ошибки;
- `validate()` каждого типа: таблица неверных примеров → ожидаемые ошибки с путями;
- строгий разбор: незнакомое поле, незнакомый тип → ошибка с путём;
- мягкий разбор: незнакомое игнорируется, `Unknown` на месте;
- разбор → запись → разбор = равные объекты.

**Готово, когда** все примеры JSON из content-format, раздел 5, разбираются, а неверные дают ожидаемые ошибки.

### Этап 2. Курс: модель, файл, архив, хранение — сделано

`core`:
- новая модель: `Course(id, name, revision, updatedAt, theme?, rules?, settings, units | topics)`,
  `Unit(id, title, subtitle?, theory: Content?, topics)`, `Topic(id, title, explanation: Content?, exercises)`;
- настройки курса: `allowTypos`;
- `CourseJson`:
  - `formatVersion` — строгий режим для своей версии, мягкий для более новой;
  - проверки курса: units xor topics, уникальность id, ссылки `seeAlso`, `alt`, совместимость политик в `rules`;
  - все ошибки сразу;
- курс, импортированный в мягком режиме, помечен «только для изучения» (не редактируется и не экспортируется);
- `CourseService`: импорт (повторный — новый курс с новыми id, занятое название получает номер «(2)»), удаление, `revision`.

`client`:
- `CourseArchive`: zip (`course.json` + `images/`) или одиночный JSON;
- проверка, что каждый `src` без `https://` есть в архиве;
- картинки: из архива копируются, по URL скачиваются при импорте;
- хранение — в `<Documents>/polylingy/images/<courseId>/`;
- новая схема SQLite: документ курса хранится тем же JSON, что и файл; старый файл базы переименовывается;
- `SampleCourse`: маленький курс с одним юнитом (теория из нескольких блоков) и упражнениями всех типов.
  Он же служит образцом в тестах.

`app`: старый экран изучения временно отключён, список курсов показывает новые курсы; импорт работает.

Образцы — в `client/src/desktopTest/resources/courses/`:
- `all-types.json`;
- `flat.json`;
- `unit-with-images.zip`;
- `invalid/*.json` — по одному на каждую ошибку;
- `newer-version.json`.

Тесты:
- импорт каждого образца;
- импорт → экспорт → импорт;
- ошибки с путями;
- мягкий режим;
- картинки из zip;
- хранение переживает перезапуск.

**Готово, когда** zip и JSON импортируются, курс переживает перезапуск, экспорт → импорт даёт тот же курс.

### Этап 3. Проверка и отрисовка упражнений и теории — сделано

`core`:
- `TextMatcher`: `match(input, variants, allowTypos): CORRECT | TYPO | WRONG`. Нормализация и опечатки —
  ровно как в learning-model, раздел 3. Большая таблица тестов: апострофы, регистр, пробелы, точка,
  слова < 4 букв, `a`/`an`, пропущенная буква не опечатка, одна опечатка на пункт.
- `ExerciseChecker` для каждого типа: `check(task, response, settings): List<ItemResult>`, по пункту на пропуск,
  выбор, пару, предложение. Выбор, сопоставление и порядок проверяются точно.

Новый модуль `:content-compose` (Compose MP, зависит от `:content`):
- `ContentTheme`: акцент (цвет курса или по умолчанию), цвета верно/опечатка/ошибка, шрифты;
- `ImageLoader` — интерфейс «src → картинка», реализует `app` (из хранилища `client`);
  `content-compose` о файлах не знает;
- `InlineText` — отрисовка `Inline`;
- `BlockView` — все блоки с правилами раскладки из content-format, раздел 4, включая узкое окно;
- `ExerciseView` для каждого типа:
  - ввод (`response`, `onChange`);
  - проверенное состояние (`results`): верно, опечатка с правильным вариантом, ошибка с правильным ответом,
    `note` под неверным пунктом;
  - клавиатура: Tab к следующему пропуску, Enter — проверить;
- `ExplanationView` — `Content` под проверенным упражнением.

Порядок работы:
1. `gaps` и `choice`;
2. `match` и `order`;
3. `table` и `pictures`;
4. блоки теории.

UI-тесты в `app/desktopTest` на экране-витрине: каждый образец до проверки, после проверки, на узком окне;
`screenshot(...)` на каждое состояние, я просматриваю PNG.

**Готово, когда** у каждого типа есть чекер с таблицей тестов и скриншоты во всех состояниях.

### Этап 4. Модель обучения: журнал, политики, `replay()`, `StudyService` — сделано

Журнал:
- новое событие ответа:

  ```kotlin
  AnswerSubmitted(courseId, topicId, exerciseId, courseRevision, response: Response, results: List<ItemResult>, …)
  ```

  Самооценки и «засчитать» нет (раздел 6). `schemaVersion = 1`.

Политики:
- интерфейсы ровно как в learning-model, раздел 5: `Phase`, `Attempt<G>`, `Round<G>`, `GradingRule<G>`,
  `MasteryPolicy<G>`, `Scheduler<M, G>` (с `dueDate(): LocalDate?`), `TopicPicker`, `Candidate`, `CourseRules<M, G>`;
- `PassFail`; `AnkiGrade` не заводим, пока нет политики, которая его использует;
- реализации — только нужные для наборов ниже:

  | Политика | Реализации |
  |---|---|
  | оценивание | `AllCorrect` (`TYPO` засчитывается, если курс разрешает опечатки), `Threshold(min)` |
  | освоение | `Consecutive(learning, review)` |
  | расписание | `Once` (выучен после первого раунда), `Ladder(days, retireAfterLast)`, `Sm2Scheduler` (перенос `Sm2Policy`: качество — число ошибок в раунде) |
  | порядок | `ReviewsFirst` (по умолчанию), `Random` (раздел 8) |

- реестр политик: `rules` из JSON (learning-model, раздел 4) → `CourseRules`, несовместимая пара — ошибка импорта;
  без `rules` — «Лестница» и `ReviewsFirst`.

Наборы:

| Набор | Оценивание | Освоение | Расписание | Для чего |
|---|---|---|---|---|
| «Быстрый» | всё верно | 1 подряд | один раз | один верный ответ — выучен |
| «Лестница» | всё верно | 3 при изучении, 1 при повторении | 1 · 3 · 7 · 14 · 30, после последней — выучен | основной для учебников |
| «SM-2» | всё верно | 3 при изучении, 1 при повторении | SM-2 | как в 0.1 |

Прогресс:
- `replay()`: журнал + курс + `CourseRules` → `TopicState<M, G>` для каждого топика. Ответы на удалённые
  упражнения и топики игнорируются. Старые ответы не перепроверяются: берутся сохранённые `results`.
- Статусы для экранов:
  - новый;
  - в процессе (раунд начат);
  - к повторению (срок наступил);
  - пройден (срок в будущем, показываем дату);
  - выучен (срока нет);
  - юнит выучен, когда выучены все его топики.
- Доступность: новый, раунд начат или срок наступил. Выученный сам не выдаётся.

`StudyService`:
- вход в юнит или в курс → кандидаты → пикер → топик;
- упражнение: случайное, не повторяет только что показанное, если есть другие;
- приём ответа: чекер → событие;
- нужна ли теория: в юните нет ни одного ответа.

Тесты:
- каждая политика таблицами;
- сценарии из learning-model, раздел 6, как тесты `replay()`;
- `Sm2GoldenTest` на новом `Sm2Scheduler`;
- `StudyService` на образцах.

**Готово, когда** сценарии learning-model проходят, а `StudyService` проводит курс-образец от нового топика до «выучен».

### Этап 5. Дизайн

На холсте, по замечаниям к третьему кругу:

- меньше академичности;

Итог — один стиль и полный набор экранов:

## 3b. Сделано на этапе 3 сверх описанного

- Чекер возвращает `ItemCheck(result, rightAnswer)`: при опечатке виден тот вариант ответа, к которому ответ был близок
  (`is wroking` → «is working», а не первый вариант «’s working»). В журнал пойдут только результаты.
- `TextMatcher` реализован строго по правилу: `then` → `than` считается опечаткой (4 буквы, одна замена),
  хотя `learning-model.md` называет эту пару опасной. Если это мешает — менять правило.
- Ширина пропуска растёт по мере ввода и не подсказывает длину ответа.
- Порядок вариантов, правых сторон и слов перемешивается по `seed` и не меняется, пока упражнение на экране.

## 3c. Сделано на этапе 4 сверх описанного

- `rules` в файле: набор (`preset`) плюс замены частей (решено с пользователем).
- Досрочная практика — обычный раунд, перепланирует топик (решено с пользователем).
- `GradingRule.grade(answer)` без отдельного `check`: результаты пунктов теперь лежат в самом событии.
- `Candidate.started`: начатый раунд пикер предлагает первым, даже если пользователь уходил с экрана.
- `StudyService.answer` возвращает статус топика до и после ответа — из этого экран строит строку прогресса.
- Эталон SM-2 проверяется с «3 подряд» и при повторении, как работала 0.1; набор `sm2` — «1 при повторении», как в плане.
- Незнакомый тип политики в `rules` — ошибка импорта даже для файла новее приложения (мягкого режима для политик нет).

## 4. Логи

Всё важное пишется в лог, чтобы по нему было видно, что делал пользователь и что происходило.

- **Что логируем:**
  - каждое действие пользователя: открыл курс или юнит, начал упражнение, проверил, перешёл дальше,
    импорт, экспорт, удаление;
  - импорт: файл, версия формата, режим (строгий или мягкий), найденные ошибки;
  - ответ: курс, топик, упражнение, результаты по пунктам, полученная оценка, переход раунда
    (освоен, новый срок, выучен);
  - хранение: открытие базы, сохранение курса, запись события;
  - старт и закрытие приложения, версия;
  - каждое исключение со стеком.
- **Чего не логируем:** содержимое курса целиком (только id и названия).
- **Где:** `content` — чистый разбор: ошибки он возвращает, а не логирует. Логи пишут `core`
  (сервисы), `client` и `app` (ViewModel — действия пользователя).
- **Как:** раздел 8.

## 5. Тесты

Покрытие подробное, по слоям:

| Слой | Что | Где |
|---|---|---|
| Модульные | разметка, `validate()`, разбор, `TextMatcher`, чекеры, каждая политика, `replay()` — таблицами | `content`, `core` |
| Эталонные | SM-2 на 200 историях из 0.1 (`Sm2GoldenTest`) | `core` |
| Интеграционные | импорт JSON и zip с настоящими файлами, хранение в настоящей SQLite, картинки, перезапуск | `client` |
| Функциональные | курс-образец проходится через `StudyService` + журнал + `replay()` от нового топика до «выучен»; сценарии из learning-model, раздел 6 | `core` + `client` |
| UI | каждый экран и состояние, путь от импорта до повторения, скриншоты, которые я просматриваю | `app` |
| Ручные | нативный диалог файла, настоящее окно, установщик | этап 7 |

Каждый этап добавляет тесты своего слоя; без них этап не считается готовым. Измерение покрытия — раздел 8.

## 6. Решено

- Текущую базу можно не сохранять: ничего ценного в ней нет.
- Ветка `next`, один мерж в `master`.
- Наборы политик «Быстрый», «Лестница», «SM-2»; по умолчанию — **«Лестница»**.
  SM-2 остаётся, если обходится малой кровью.
- Порядок: `ReviewsFirst` по умолчанию — сначала повторения, потом новые топики **по порядку**
  (юниты по очереди, топики в юните по очереди). Для плоских курсов можно выбрать `random`: повторения, потом новые в случайном порядке.
- **Самооценки и «Я был прав — засчитать» в 0.2 нет.** Позже они добавятся без смены интерфейсов: это новое необязательное
  поле в событии ответа, правило оценивания, которое его читает, и настройка курса «показывать кнопку».
  Что значит «засчитать» при шкале из 4 оценок, решит само правило оценивания.
- **Итог после проверки — две независимые строки:**
  - что сказала проверка — только из результатов пунктов, одинаково для всех типов упражнений:
    «All correct», «1 typo», «1 mistake», «2 mistakes»;
  - что изменилось в прогрессе — только из состояния топика до и после ответа: «Topic passed — next review Thursday»,
    «Topic learned», иначе ничего.

  Об оценке `G` экран не знает. Слова вроде «Almost», намекающие на засчитано/не засчитано, не используем:
  при пороге 75 % ответ с одной ошибкой засчитан.
- **Управление курсами откладываем:** редактирование, добавление топиков и упражнений, визуальный редактор,
  повторный импорт с обновлением. В 0.2:
  - курсы добавляются **кнопкой «Импорт»** (JSON или zip), при первом запуске есть пример курса;
  - повторный импорт создаёт **новый курс** с новыми id, как сейчас;
  - если название уже занято, к нему добавляется номер: «English Grammar in Use (2)»;
  - кнопка «Добавить топик» в плоских курсах остаётся **заглушкой**; кнопки «Новый курс» нет.

## 8. Инструменты

- **Логи:** `kotlin-logging` (обёртка над SLF4J для Kotlin, работает во всех модулях KMP) + logback на десктопе.
  Файл `<Documents>/polylingy/logs/polylingy.log`, новый каждый день, хранятся 14 дней. Уровни:
  - `ERROR` — исключения;
  - `WARN` — что-то пошло не так, но работа продолжается (курс новее приложения, картинка не скачалась);
  - `INFO` — действия пользователя, импорт, ответы, переходы раунда, старт приложения;
  - `DEBUG` — подробности: выбор пикера, промежуточные состояния `replay()`.

  В файл пишется `INFO` и выше.
- **Покрытие:** Kover — официальный Gradle-плагин JetBrains. Пока идут тесты, он замеряет, какие строки выполнились,
  и строит HTML-отчёт. Подключается одной строкой в модуле. Порог 90 % строк для `content` и `core` проверяется
  в `./gradlew check`, для `app` порога нет. Если окажется заметно тяжелее, чем ожидаем, — убираем.
- **Порядок `random`:** сначала повторения, потом новые топики в случайном порядке.

## 9. Вернуться позже: настройки и политики курса

Сейчас (этап 2) в файле курса есть два объекта, и оба — внутри документа курса:

```json
"settings": { "allowTypos": true },
"rules": { "grading": …, "mastery": …, "scheduler": …, "picker": … }
```

**Решено пока:** настройки и политики — часть курса, ими управляет автор курса; лежат в JSON документа.
Это самый простой вариант; перенести их потом в отдельную таблицу несложно. Вернуться, когда будет готов
дизайн экранов (настройки курса, выбор политик), и ответить:

1. **Опечатки — это настройка или политика?** Сейчас `allowTypos` — отдельная настройка. Но по `learning-model.md`
   проверка всегда может сообщить `TYPO`, а засчитывать ли его — дело оценивания (`GradingRule`). Тогда
   `allowTypos` логичнее сделать параметром оценивания (`"grading": { "type": "all-correct", "typos": "count" }`),
   а `settings` убрать.
2. **Чьи это решения — автора курса или ученика?** Содержание курса пишет автор, а «как строго меня проверять» и
   «как часто повторять» может захотеть поменять сам ученик, не трогая курс.
3. **Где хранить.** Если политики — выбор ученика, их место не в документе курса (он меняется только импортом),
   а в отдельной таблице «политики курса» рядом с курсом. Тогда в файле курса остаются разве что
   рекомендуемые автором политики по умолчанию.

До этого: оба объекта читаются из файла курса и хранятся вместе с ним; `rules` начнёт работать на этапе 4.
